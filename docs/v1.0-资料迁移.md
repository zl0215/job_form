# v1.0 旧版资料迁移（profile.json → 新扩展）

日期：2026-11-09。对应共享任务 T3。本文说明如何把旧版 Python「校招表单助手」保存的
`%LOCALAPPDATA%\CampusFormAgent\profile.json` 一次性迁移到新浏览器扩展的 `UserProfile`，
以及迁移范围、去重规则、别名规则、未迁移项和验证边界。

> 约束（与 `AGENTS.md` 一致）：迁移只搬运已保存的原始事实与旧语义映射，不生成、不编造任何答案；
> 去重不覆盖冲突值；文档、摘要、日志都不输出个人答案值；本文中的条数来自真实资料的离线只读校验，
> 不含任何具体个人值。

## 1. 入口与操作

设置页 →「数据与同步」→「从旧版校招助手导入（profile.json）」：

1. 选择旧版 `profile.json`（`accept=".json,application/json"`，上限 20 MiB）；
2. 浏览器本地 `JSON.parse` + `convertLegacyProfile()` 转换（纯函数、不联网、不依赖 chrome API）；
3. 只显示**条数摘要**与通用提示（不显示任何个人值、不回显文件内容）；
4. 点击「覆盖并导入」后弹出二次确认；
5. 确认后通过既有 `SAVE_USER_PROFILE` 消息写入**当前活动简历**（携带 `expectedProfileId`，
   若期间切换了简历会被后台拒绝，不会覆盖别的资料）；成功后提示
   「已导入，可在基本信息/教育经历等页面核对」。

其它简历不受影响；导入不能撤销，建议先做一次「本地 JSON 备份 → 导出完整数据」。
解析失败/结构不符时不会改动本地数据，并给出明确错误：
旧资料根结构无效、`facts` 结构无效、`records` 结构无效、`schemaVersion` 不支持、
误选新扩展备份文件（会提示改走「导入完整数据」）。

## 2. 迁移范围

读取并迁移的旧资料段落：

| 旧段落 | 用途 |
|---|---|
| `facts` | 27 项已保存的个人事实 |
| `records` | 8 个记录模块（教育/项目/证书/家庭/语言/实习/获奖/论文） |
| `mappings` | 旧页面字段映射；只取 `status=ready` 的标签，作为别名来源/交叉核对 |
| `semanticLinks` | 旧工具的语义关联（`label/section/type/options → canonicalKey`），是旧资料里唯一保存 `canonicalKey` 的地方 |

不迁移的辅助段：`preferences`、`definitions`、`aliases`、`aliasBlocks`、`fieldVersions`、
`redirects`、`bindings`、`pages`、`pending`、`attachments`、`policy`、`resumeSource`、
`resumeUnmapped`。原因：这些是旧工具按站点保存的页面观察/学习/绑定状态，新扩展会在真实页面
重新学习；导入时会以统计提示列出数量，不静默丢弃文件。旧资料本身**只读**，不做任何修改。

| 旧模块 | 新模型 | 字段映射 |

| 实习经历 | `experience[]` | `role→position`、`start/end→startDate/endDate`、`description`；旧资料无单位字段时 `company` 留空并提示补齐 |
| 获奖经历 | `awards[]` | `name/date` 核心；`role/description` 原样；未知字段保留 |
| 证书 | `certifications[]` | `name/date` 核心；`issuer/credentialId` 有则保留；`description` 等其余内容保留到 `customInformation`（名称“证书说明”等） |
| 家庭信息 | `customModules.family`（预设模块） | `name/relationship(title)/organization(employer)/position/phone`；成员姓名、单位、职务、电话按预设标记为敏感；未知字段追加为模块记录字段 |
| 语言能力 | `customModules.languages`（预设模块） | `type→language`、`proficiency→level`、`score/level/workLanguage/obtainedAt` 有则保留；事实里的“英语水平”若与同名英语记录的 level 冲突，不覆盖记录值，另存于 `personal.englishLevel` 并提示 |
| 论文发表 | `customModules.papers`（预设模块） | `name→title`、`journal→venue`、`date→publishedAt`、`author_order→authorRank`、`type/status` 有则保留；未知字段追加为模块记录字段 |

其它规则：

- `fields` 与 `identityHints` 合并读取：正文字段优先，`identityHints` 只补空缺；两者不一致时
  保留正文字段值并计数提示（真实资料中出现 2 处，见 §8）；
- 未知记录模块：原样转换成同名自定义模块（`repeatable=true`），并提示；
- 空记录（没有任何字段值）跳过并计数；
- 每个记录/模块记录都生成新的稳定 ID 与预设字段结构，便于设置页编辑。

## 5. 教育经历去重规则

身份锚点（与任务约定一致）：

```
anchor = 规范化(学校) + 规范化(学历) + 规范化(入学时间→YYYY-MM) + 规范化(毕业时间→YYYY-MM)
规范化 = NFKC + 去除空白；日期尽量归一到“年-月”，无法解析则用原文
```

- 只有锚点**完全一致**的记录才合并；合并时选“非空字段最多”的记录为基准；
- 同组其它记录只用来填补基准的空字段；两边都有值且不同时**不覆盖**，保留基准值并计数提示；
- 锚点不同但同校的记录不自动合并（可能对应本科/硕士两段，或起止时间不同的扫描），
  只输出“同校记录未自动合并”的提示，由用户在设置页人工核对/合并；
- 缺少学校名的记录保留，不丢弃，提示人工补充。

真实资料校验（只读离线，不含具体值）：教育记录 8 条 → 身份锚点 8 组，**完全重复 0 条**
（可合并 0 条），同校但锚点不一致 2 组，缺学校 2 条。也就是说旧资料里的“8 条”并非完全重复：
部分扫描缺学历/日期或起止时间不同。按 `AGENTS.md` “冲突值不得因去重而覆盖”，这里不做模糊合并，
只提示人工核对；不能为了凑成 2 条而覆盖掉可能真实存在的多段教育或不同日期。

## 6. 旧页面字段别名迁移（fieldAliasOverrides）

目标：把旧工具“已经认得”的页面标题迁移为新扩展的永久别名，减少后续重填。

来源与规则：

1. 旧 `mappings` 只取 `status=ready`（真实资料 214/922 条）；
2. 旧 `mappings` 的 `canonicalKey` 在真实资料中**全部为空**（0/922）。因此以
   `semanticLinks`（63 条，唯一保存 `canonicalKey` 的段落）作为语义来源，并仅对 `ready` 映射做交叉核对；
3. 关联方式：先按 `[label, section, type, options]` 精确匹配，再退回 `[label, section, type]`；
4. 旧 `canonicalKey` → 新稳定 key（`fieldAliasOverrides` 的 key，与匹配候选 key 一致）：

| 旧 canonicalKey | 新稳定 key |
|---|---|
| `basic.household_location` | `personal.householdRegistration` |
| `basic.hometown` | `personal.hometown` |
| `basic.gaokao_location` | `personal.gaokaoLocation` |
| `basic.current_city` | `personal.currentAddress` |
| `basic.student_origin` | `personal.studentOrigin` |
| `basic.address` | `personal.mailingAddress` |
| `basic.height` / `basic.weight` | `personal.height` / `personal.weight` |
| `basic.highest_degree` | `personal.highestEducation` |
| `basic.highest_school` / `basic.highest_major` | `education.school` / `education.major` |
| `basic.graduation_date` | `education.endDate` |
| `emergency.name` / `emergency.phone` | `personal.emergencyName` / `personal.emergencyPhone` |
| `family.title` / `family.position` / `family.phone` | `module.family.relationship` / `module.family.position` / `module.family.phone` |
| `education.school` / `college` / `major` / `gpa` / `rank` / `mode` / `start_date` / `major_category` | `education.school` / `education.college` / `education.major` / `education.gpa` / `education.ranking` / `education.educationType` / `education.startDate` / `education.majorCategory` |
| `experience.role` | `experience.position` |
| `project.description` / `project.start_date` | `project.description` / `project.startDate` |
| `language.type` / `level` / `score` | `module.languages.language` / `module.languages.level` / `module.languages.score` |
| `publication.name` / `author_order` | `module.papers.title` / `module.papers.authorRank` |
| `preference.salary` | `module.jobIntent.salaryExpected` |

5. 标签清洗与安全过滤（不迁移的情况会在提示里计数）：
   - 去掉首尾空白、必填星号/问号/冒号；
   - 长度 > 40、包含 `----`、含 3 个以上年份、`/` 超过 4 个的“选项列表型”标题不迁移；
   - 过于通用的标题（如“姓名”“手机号码”“关系”“时间”“学校”等）不迁移，避免把页面字段绑错；
   - 同一个标签对应多个新字段时只保留第一个；
   - 同一个字段下重复标签去重。

真实资料校验（只读：只输出计数）：ready 映射 214 条，其中 28 条能定位旧语义键；
旧语义关联 63 条一起构成 91 条候选，最终迁移别名 **48 条、覆盖 29 个字段**；
未写入的候选为：22 条重复标签、16 条旧语义键在新模型中没有对应字段、5 条标签不安全/过于通用。
另有 186 条 ready 映射因为没有语义键而完全没有进入候选
（旧资料根本没有保存这些映射的 `canonicalKey`，不是本次实现漏迁）。

## 7. 未迁移项与原因

| 项目 | 原因 |
|---|---|
| `certificate.name` / `date` / `description` 的旧页面标题 | 新模型的证书没有对应的匹配候选 key（证书走结构化字段，不参与候选别名）；数据本身已迁移到 `certifications` / `customInformation` |
| `education.full_time`（是否全日制）的旧标题 | 旧值是“是/否”，新字段语义是“培养方式/学习形式”，把是/否别名挂过去会误填；记录内已保留原值 |
| `education.degree_country`（学校所在国家/地区） | 新模型无明确对应字段；未迁移 |
| 186 条无 `canonicalKey` 的 ready 映射 | 旧资料没有保存语义键，无法确定目标字段；不猜测，只计数提示 |
| 非 ready 状态映射（review/incompatible/unmatched/missing） | 旧工具自身也未确认可填，不迁移为永久别名 |
| 旧辅助段（preferences/pages/pending/bindings 等） | 旧工具的页面观察/学习状态；新扩展在真实页重新学习 |
| 教育记录中的冲突值、缺失学校/单位 | 不自动修正、不覆盖；保留原记录并提示人工核对 |
